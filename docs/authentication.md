# Authentication and session model

Production uses Google Cloud's authenticated reverse-proxy boundary (Identity-Aware Proxy or an equivalent Cloud Run ingress that emits verified `X-Goog-Authenticated-User-*` headers). The Express API derives `/api/me` from those verified headers and never accepts a browser-supplied user id. Every project, upload, analytics result, and asset route checks the persisted owner id.

For IAP, configure the OAuth consent screen and request `openid`, `email`, and `profile`. YouTube authorization is separate and belongs to the ingestion worker; it requests `youtube.readonly` and `yt-analytics.readonly`. Add the IAP callback generated for the protected application to the Google OAuth client's authorized redirect URIs. For a custom OAuth proxy, configure its exact HTTPS callback, for example `https://dailies.gurlzine.com/oauth2/callback`.

The browser session is the secure, HTTP-only cookie managed by the identity proxy. Dailies does not store passwords or identity tokens in local storage. Signing out redirects to the configured identity-provider logout URL (`VITE_SIGN_OUT_URL`).

Development and production both require the same verified Google identity boundary — the API does not accept a project owner id from the browser and has no fixture, offline, or synthetic identity path. What differs is which boundary verifies the identity:

- **Production**: Identity-Aware Proxy (or an equivalent authenticated ingress) sits in front of the API and injects verified `X-Goog-Authenticated-User-*` headers, as described above.
- **Deployments with no IAP-fronted ingress** (e.g. a local or hackathon dev server hitting production Firestore/GCS/Vertex directly, with no HTTPS load balancer in front of it): IAP headers can never appear, since IAP is infrastructure that only exists in front of a deployed HTTPS endpoint. `api/src/googleSignIn.ts` covers this case with a real, cryptographically verified Google sign-in — `GET /api/auth/google/start` redirects to Google's consent screen, `GET /api/auth/google/callback` exchanges the code and verifies the returned ID token against Google's public keys (rejecting anything with an unverified email), then the API signs its own short-lived session cookie from that verified identity. The API still never trusts a client-asserted user id; it only trusts what it verified itself. This path only activates when `GOOGLE_SIGN_IN_CLIENT_ID`, `GOOGLE_SIGN_IN_CLIENT_SECRET`, `GOOGLE_SIGN_IN_REDIRECT_URI`, and `SESSION_SECRET` are all set — leave them unset on any deployment that has a real IAP ingress.
